# STU 外卖查询与选餐（开发版）

新增 7 个 MCP 工具，可按实际餐段和区域搜索商家、查看配送批次/截单时间、菜单和规格，再生成选餐清单。
这是独立第三方平台，不是学校官方信息。当前功能不创建订单、不付款、不修改微信
购物车或个人地址。沿用本项目的 stdio / Streamable HTTP 两种接入，无需运行微信、
抓包程序、浏览器或桌面。

## 配置

由操作者在 MCP 宿主上，将已验证的本机 API 配置导入现有加密凭据库：

```sh
stu-mcp takeout configure --file /private/path/client.json
stu-mcp takeout status
```

配置含 `userId`, `appletId`, `apiToken`, `salt`, `signToken`；来源必须为当前小程序。
配置文件是一次性导入来源，运行时只读取 Vault，不退回明文文件。默认使用已批准的
OS keyring，个人服务器可沿用显式外置主密钥后端。不内置真实签名材料，不通过 MCP
参数、聊天或客户端配置收取凭据。

不自动读取环境代理。导入文件可明确给出无用户名/密码的回环 HTTP 代理 `proxy`，
供这个来源单独使用；没有配置则直连。不会改变系统、客户端或其他来源的网络设置。
可选的 `headers` 仅接受已核验的 User-Agent、Referer、Accept 和 xweb_xhr。

移除这个来源的配置：

```sh
stu-mcp takeout remove
```

`status` 的配置已保存不代表当前在线可用。没有配置只影响外卖功能，不要求学校账号，
也不影响原来的校园查询。MCP 宿主与当前聊天客户端可能不是同一台机器，配置须在
实际提供 MCP 的宿主完成。

## 工具

| 工具 | 用法 |
| --- | --- |
| `search_takeout_shops` | 按平台分类和 `area_id` 搜目录，返回区域目录及实际生效筛选；平台餐段分类不覆盖本部普通商家 |
| `find_takeout_meal_shops` | 在显式区域逐页核对店铺实际配送批次，按日期和餐段筛选，单列未知条目 |
| `get_takeout_shop` | 用 `shop_id` 获取公开详情及平台下单规则代码 |
| `get_takeout_delivery_slots` | 指定店铺、北京时间日期和餐段，查询批次、提前分钟数与截单状态 |
| `get_takeout_menu` | 商品和分类；按名称/分类本地过滤、分页 |
| `get_takeout_product` | 用店铺与商品 ID 获取规格组选项、加价和包装费字段 |
| `prepare_takeout_selection` | `items=[{"product_id":"...","quantity":1}]` 生成普通标价选餐清单 |

目录/菜单每次返回 1–50 项，列表分页是完整响应的本地切片；实际餐段查店每次扫描1–10条。
30 秒内复用进程缓存；查询工具可用 `refresh=true` 再读。HTTP 有连接/读取空闲超时和
响应体大小限制，不承诺整个多店扫描的固定总耗时；不跟随跳转，不自动重试，不访问
任意 URL 或未知接口。

例如可以对 agent 说：“搜索奶茶店，看看其中一家有哪些 15 元以内的商品，再查商品
规格，帮我列一份选餐清单。”标价筛选不意味着最终结算也在预算内。

CLI 同样可用：

```sh
stu-mcp takeout shops 奶茶 --limit 10
stu-mcp takeout shops --meal-period 午餐 --area-id 72502
stu-mcp takeout meal-shops --area-id 65868 --meal-period 午餐 --scan-limit 5
stu-mcp takeout meal-shops --area-id 76624 --meal-period 晚餐 --offset 5
stu-mcp takeout shop 448721
stu-mcp takeout menu 448721 --query 汉堡
stu-mcp takeout slots 448721 --date 2026-10-22 --meal-period 午餐
```

## 餐段与区域

商家列表的 `meal_period` 对应平台明确命名的分类：午餐、晚餐、下午茶、即点即送、
本部宵夜、东校区宵夜（英文别名也可）。分类 ID 从当前响应中解析，不硬编码。
仅说“宵夜”而平台同时存在两个校区分类时，工具要求明确校区，不自行猜测。

`area_id` 留空使用宿主原配置；`"0"` 明确选择全部区域。返回 `filters` 说明实际区域和
分类，`areas` 给出区域 ID、名称及父级，商家 `delivery_area_ids` 来自其配送区域字段。
平台把“本部”“本部宵夜”“东校区”“东校区宵夜”等列为不同区域，不能互相替代。
全区域命中的店不保证能配送到某个地址，也不证明本人所在校区。

| --- | ---: | ---: | ---: |
| 全部（0） | 96 | 104 | 48 |
| 本部（65868，原默认） | 0 | 0 | 0 |
| 东校区（72502） | 92 | 100 | 未在本轮查询 |
| 东校区宵夜（77202） | 未在本轮查询 | 未在本轮查询 | 47 |

表中午餐/晚餐均指**平台同名分类命中**，不是实际支持该餐段的店数。后续核对发现，
本部普通目录按快餐、粉面等分类，未挂入平台的午/晚餐分类，但多家店有午/晚配送批次。
因此本部用户应留在本部区域，改按实际批次查询；不能为获得非空结果切到东校区。
已识别的完整列表响应可能省略 `shopList`，前端将其显示为空，本工具同样返回空并注明
`list_reported_by_source=false`；未知或损坏的响应仍报告结构变化。空结果不推断关店、
截单或永久无店，数量与区域目录会随平台变化。

### 按实际餐段查本部商家

例如 `find_takeout_meal_shops(area_id="65868", meal_period="午餐", date="2026-10-23")`。
它读取该区域目录的一页（默认5条，上限10条），逐条读取已核验的规则接口，再按批次
开始时间筛选餐段和日期；不读取菜单，也不跨校区补全结果。

- `candidate_total_count` 是目录候选条数；`scanned_count` 是本次实际检查条数。
- `matched_in_page` 与 `items` 只描述本页有已知匹配批次的记录，默认要求未截单。
- `unknown_items` 保留无固定批次、未知格式/规则或读取失败的条目。即时配送并不一定有固定批次。
- 用 `next_offset` 继续下一页，直到 `has_more=false`；本页零命中不等于区域无店。
- `include_closed=true` 可研究已截单、停用或预订关闭的已知批次，未知约束仍单列。

实际库存、营业限制和地址可配送性未经本工具验证；目录中出现公告不代表它是可点餐的店。
一次业务读取绑定同一配置版本，包括缓存命中和多步读取；中途配置改变或退出会丢弃整次结果。

## 配送批次和截单

`get_takeout_delivery_slots(shop_id, date="", meal_period="", include_closed=true, refresh=false)`
以 `Asia/Shanghai`（UTC+08:00）计算，日期留空表示北京时间今天，与 MCP 宿主或调用方
时区无关。返回 `evaluated_at`、`business_today`、允许预订的日期、营业时间及逐批次：

- `delivery_start` / `delivery_end`：含日期和时区，可跨午夜；单点批次的结束时间为 `null`；
- `advance_order_minutes`、`cutoff_at`：批次开始减提前分钟数；
- `time_status`：未截单、已截单、日期窗口外、平台停用/未开启预订，或未知；
- `passes_time_constraints`：仅截单和预订日期窗口是否通过；未知为 `null`。
  `time_constraint_scope=cutoff_and_booking_window`，未核验营业时间限制或实际结算可用性。

批次自己的正数 `advanceOrderMinutes` 优先，否则使用店铺 `customTakeoutBookTime`；
`advancePrintMinutes` 是打印相关字段，不拿来计算截单。例：示例店 21:20–21:40 的批次
提前 60 分钟，因此 20:20:00 截单。边界使用精确时间，超过该时刻即标记已截单；前端
展示层按分钟判断，最后一分钟的显示可能不同。

预订天数 `2` 表示今天和明天，`-1` 表示仅明天，空值依已观察前端规则默认 7 天。
跨天批次也校验实际配送开始日；不能用窗口最后一天的“次日”批次越过预订日期范围。
过大或不认识的天数、提前时间等返回未知，不据此承诺可选。旧版时间字段优先于新版，
未核验的旧格式返回 `unsupported_format`；无固定批次返回 `not_reported`，均不代表没有
即时配送。营业时间单独返回，不当作配送时间或当前营业证明。

批次没有明确餐段名称时，按开始时间推断：05–10 早餐、10–14 午餐、14–17 下午茶、
17–20 晚餐、20–次日05 宵夜。结果明确标为 `meal_period_inferred`；这套便于查询的分段
不冒充平台商家列表的餐段分类。`include_closed=false` 保留未截单或未知批次。
店铺详情也附上当天批次。只缓存原始规则 30 秒，每次调用重算截单状态。

例如可说：“看看东校区明天午餐有哪些店，再查这家的配送批次和最晚几点选餐。”
工具只核算时间约束；节假日、库存、地址、商家临时状态和最终结算仍需微信确认。

## 价格与数据范围

`base_price` 是普通标价；`provider_display_price` 来自商品详情，可能是当前促销展示值。
`option_groups` 给出组 ID、是否必选、平台选择模式/数量代码，以及选项 ID、名称和加价。
这些不证明最终库存或结算价格。店铺规则代码保留原义，不把未知模式猜成“当前可下单”。

清单中的 `base_price_total` 用 Decimal 汇总普通标价，未计入规格、优惠、打包、配送或
会员规则；返回 `submitted=false`、`order_id=null`。请到微信核对规格、地址、时间和
实际应付金额。当前没有订单提交、支付、取消、领券或地址修改工具。

工具只输出明确允许的业务字段，不透出源响应的个人对象、签名参数、跳转授权链接。
数据带来源与采集时间，并标记为不可信源数据；不执行商家文案中的指令。
缓存仅在进程中，配置改变或移除后不再复用旧来源结果。

## 实测与待验

2026-10-21 本机原生 MCP stdio 已完成真实调用：奶茶搜索 12 家，示例店铺 91 项商品，
示例商品 2 组/10 个规格选项，清单生成成功且没有订单请求。7 个固定目录/规则读取
接口已核验；这些数量会随平台变化。

登录、已有地址与确认页初始化在独立协议研究中已抓到。个人地址、优惠、确认页
尚未暴露为本项目 MCP 工具，也没有将个人登录 token 导入本项目。当前账户的优惠券
入口未返回券列表，适用券/叠加和最终报价待有实际场景时核验。
真实订单、支付和回执按用户实际点餐需求另行研究，不用真实交易验收查询功能。
自动化、原生 MCP 和真实读取的范围分别记录在[验收记录](verification/2026-10-21-takeout.md)。

后续本部调查已保留10条成功的代表店规则快照；批量读取期间出现持续平台拒绝、结构
异常和网络失败，已停止采集，没有完成220条目录的全部批次核验。新实际餐段工具的
本机原生 SDK 可发现45项工具，最近一次真实业务读遇到网络失败；不要将发现成功或
合成测试通过描述为该次真实业务读取成功。历史成功样本与本轮失败分别记录。
