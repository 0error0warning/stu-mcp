## 完整流程进入 MCP 与性能核对（2026-10-19，未发行）

按用户要求把实战流程写入适配器：增加匿名直连预检、保留独立浏览器的显式直连、提交前读取本人列表并生成完整确认预览、确认后一次发送，以及新增列表记录和详情的核对。`check_repair_submission` 只读恢复未知结果或刷新处理状态，总工具数为36。MCP 不修改系统代理/Clash，也不导入用户原浏览器的密码或会话。

回执需唯一新增记录、表单生成时间、标题、单号与详情链接一致，详情17项业务值全部相符且有明确处理状态。只返回单号、稳定详情链接、状态及核对时间；回执刷新失败保留历史证据并标记 `receipt_fresh=false`，不抹成“未提交”。同一业务内容的重复请求指纹排除学校自动生成时间，不能靠打开新表单绕过。失败后的查单使用同一登录上下文的独立只读页，避免与原错误页切换互相干扰。

正式提交仍由已确认的 `btn_OK` 点击触发，但放行后通过 Playwright 内部请求上下文一次发送，`max_redirects=0`、`max_retries=0`，不读取或输出认证头和响应正文。响应统一转为中性的待核对页，随后只做固定列表/详情 GET；302、307、308 均不会重放POST。回环 HTTP 服务验证一次真实 HTTP POST、响应 Cookie 留在 Playwright 内部上下文，并在无效代理环境下正常工作。未为这些测试创建新的真实学校单据。

首轮合成回归暴露两个问题：HTTP302夹具跳转可能绕过路由拦截、响应丢失后原错误页可能仍在切换。前者仅产生匿名 GET，正式POST始终被合成路由截获；现将合成学校浏览器设为离线并以脚本导航提供列表，所有意外请求都中止。后者改为独立只读结果页，已覆盖学校已建单但响应丢失的恢复场景。错误不被隐去或当成学校成功证据。
