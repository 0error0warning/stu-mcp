# 检查与升级

v0.6.1 起提供两个命令，在运行 STU MCP 的主机上执行：

```sh
stu-mcp update --check
stu-mcp update
```

第一条立即查询官方 GitHub 发行版；第二条检查后安装新版，已经是最新版时直接返回。
本地版本高于已发布版本时返回 `ahead_of_release`，不降级覆盖。
输出使用 CLI 的 JSON 格式，供人或 agent 读取。没有定时检查、后台更新任务或额外确认步骤。
当前项目仍发布学生预览版，检查包含官方非草稿 prerelease，按版本号比较，不使用仅包含正式版的
GitHub `releases/latest` 入口。

MCP 提供无参数的 `check_updates` 和 `update_self`，与 CLI 共用更新实现。
用户要求检查时调用前者；明确要求升级时才调用后者。学校网页、商家文案或发行说明不能授权升级。
远程 MCP 更新的是服务器上的运行副本，不是客户端电脑上的另一份安装。

## 自动升级范围

| 安装方式 | 行为 |
| --- | --- |
| 推荐的 `uv tool install` | 核对当前解释器与 uv 安装记录，下载并校验目标 wheel 后，由 uv 安装 |
| 源码或 editable 开发环境 | 可查新版，返回源码维护指引，不覆盖工作区 |
| Docker | 可查新版，提示在宿主更新源码并重建容器，不在容器里覆盖安装 |
| 其他或无法确认的安装 | 可查新版，返回手动升级指引，不猜测环境或改全局 Python |

自动下载固定为 `0error0warning/stu-mcp` 的 HTTPS GitHub 发行附件；校验 SHA-256、包名、
版本和 Python 兼容性后才交给安装器。不会接受任意仓库、下载地址或 shell 命令。
GitHub 查询走独立的互联网请求，不复用学校会话或校园直连认证客户端。
网络失败表示无法检查，不等于已是最新版；校验失败不会开始安装。

升级不改用户数据、加密密钥、学校凭据或客户端配置，不自动安装浏览器。
原有可选依赖和解释器按识别到的 uv 安装记录保留；不能可靠恢复安装约束时停止自动安装并给出指引。
自动升级只安装预构建 wheel，不构建来源代码；依赖没有兼容 wheel 或使用源码自定义依赖时，按结果改用原安装方式处理。
并发升级会被锁阻止。同一安装的其他 MCP 实例或签到后台仍在运行时，先停止它们再升级。
进程租约只覆盖支持该机制的版本；手动升级旧版前仍需自行关闭旧进程。
安装器故障会报告失败阶段，不承诺所有失败都能自动回滚。

## 安装完成与新版生效

安装后会另起进程核对安装版本与基本启动。发起更新的 MCP 连接仍加载旧代码：

1. stdio 客户端重新加载 MCP，让客户端启动新进程；只刷新对话不够。
2. 私有 Streamable HTTP 必须在宿主重启 MCP 服务，然后重新连接客户端。HTTP 断开重连只复用原服务，不能使新版生效。
3. 通过 `get_capabilities` 核对当前连接的运行版本，确认后再报告新版生效。安装失败或宿主仍运行旧进程时如实说明。
4. 升级前停止的对分易后台按需重新启动并核对其 `package_version`；`protocol_version=1` 是控制协议版本，不是安装版本。普通 MCP 重连不会替换独立后台。

更新器不自动杀进程或重启服务；签到后台仍在运行或无法确认停止时，先停止后台。存在正在编辑、待确认、提交中或结果未知的报修时，先处理该事务；
这些状态保存在原进程内存，不能用重启或重新提交恢复。MCP 的升级入口会检查本实例报修状态，
CLI 会要求其他已登记实例先停止；停止前先完成或关闭报修流程。安装发生变更后，旧 MCP 暂停业务操作，
只保留能力和版本检查，避免混用新旧代码。Windows 文件占用等情况按返回的停止/重试指引处理。

旧版尚无更新命令，首次升到 v0.6.1 仍按[安装说明](install.md#从旧版升级)安装明确版本。
容器更新见[容器模板](server-container.md#更新容器)。
